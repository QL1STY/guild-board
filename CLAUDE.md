# Guild Board

A Windows companion for Genshin Impact, an unofficial fan project. It reads a HoYoLAB account the player logs in to and keeps their data on their own PC. How the parts fit together: `docs/ARCHITECTURE.md`.

## Rules that are never broken

- Never create, modify or delete anything in the game's install folder or the game's registry key. The only files of the game's it ever reads, read-only, are: when the player presses Import on the Pulls or Ledger page, its log (for its data folder, and the history link the game writes there when the player opens Feedback) and the wish-history and Feedback history links in its web cache, of which it uses the newest that answers. A wish key goes only to the wish history and a Feedback key only to the game's history logs, and either is held in memory alone, for a day at most; and, only while the player has the gallery turned on, its log (for its data folder) and the pictures directly inside the `ScreenShot` folder next to the data folder, listed and read, never written, moved or deleted.
- Never open a handle to the game process, read or write its memory, inject into it, hook it, send it input or capture its screen. The only allowed knowledge about the game is whether it is running, read from the Windows process list.
- The HoYoLAB session token lives only in `token.bin` (DPAPI). It never goes into a log, an API response, the database, a test fixture or a commit. It reaches the shell only over the core's private channel on its standard input and output (`shellchannel.py`), for the login, verify and map views, and never over HTTP.
- Guild Board's own requests go only to hoyolab.com, hoyoverse.com and mihoyo.com, and to one exact address on GitHub for Paimon.moe's public achievement list, fetched only when the player asks, and, for the installed copy alone, to the player's releases repository on GitHub, `QL1STY/guild-board-releases`, to look for a newer version and download its installer, which is checked against its signature before it is run (`netpolicy.py`, `selfupdate.py`). Beyond those, Guild Board may download public pictures from other sites, such as the Endgame headers, and sends nothing of the player's with them: each at an exact address written in one table in the code (`netpolicy.PUBLIC_PICTURE_URLS`), through `netpolicy` alone, as a plain GET with Guild Board's user agent and no cookie, token, key or identifier of the player, following no redirect, up to 8 MB a picture, into the art cache. A URL taken from a HoYoLAB response is never sent to a host outside HoYoverse's. The HoYoLAB login, the keys, anything read from the account and anything from the game's folders still go only where they go above. Only read account data, with two exceptions: redeem a gift code that the player typed, pasted or clicked to redeem, and claim the day's check-in reward when the player presses Claim, never by a timer, a sync or a start. The wish history and the game's history logs are also read automatically with read-only keys that HoYoverse's `genAuthKeyByCookieToken` gives the stored login: only `account_id_v2`, `account_mid_v2`, `cookie_token_v2` and `lrsag` go there, the keys are held in memory alone and never stored, and that refresh reads no file of the game's.
- Guild Board reads HoYoLAB's calculator as the player set it up and never switches its sync on; beyond the two exceptions above it never writes to HoYoLAB. The Characters pages add two reads of the stored login: the detailed characters (`character/detail`) and the batch calculator (`batch_compute`, with explicit levels, through `client.batch_calculator(` in `_batch_compute` alone). The names `_enable_calculator_sync` and `avatar/auth` appear nowhere in `src/guildboard`. Once the player has given the first run's consent, the HoYoLAB wiki's lists, entries and pictures are also read automatically, through `netpolicy` only: each list at most once a day and each entry once for a game version, from `sg-wiki-api.hoyolab.com` (the list request is a POST that only asks for a list), and pictures from `act-webstatic.hoyoverse.com`, `act-upload.hoyoverse.com`, `upload-static.hoyoverse.com`, `bbs.hoyolab.com` and `fastcdn.hoyoverse.com`, up to 8 MB a picture. Nothing is asked of the wiki before consent.
- Guild Board's online features talk to one exact host, the player's Supabase project (`netpolicy.CLOUD_HOST`, through `netpolicy.fetch_cloud`), and only after the player signs in with Discord. Only the player's profile (their name, UID, AR and HoYoLAB picture link), the stats they switched on, their pins, their presence, friend requests and their own synced data go there. Never the HoYoLAB token or cookies, a wish or Feedback key, a HoYoLAB response or anything from the game's folders. The account's session lives only in `cloud.bin` (DPAPI) and follows the token's rules.
- `genshin` is imported only in `src/guildboard/sources/hoyolab.py`.

`tests/test_handsoff.py` enforces these. If it fails, fix the code, not the test.

## Working here

- Python 3.12 with uv. Run the whole suite with `uv run pytest -n auto` (every core), and one file while you work with `uv run pytest tests/test_x.py`. Run the Python suite and the browser tests one after the other, not at once. A few tests (the PowerShell scripts', the window's) need Windows.
- Set up a fresh checkout with `powershell -ExecutionPolicy Bypass -File setup.ps1`. It quits a running Guild Board, installs, builds the interface and the shell and makes the desktop shortcut.
- `setup.ps1` also makes a copy of Electron's program named for Guild Board, in `shell\app-dev`, for the desktop shortcut (`shell/scripts/make-app-dev.mjs`): it keeps the name `electron.exe`, so the shell stays in development mode, and is made again only when Electron's version or the icon changes.
- Run Guild Board with its window on demo data with `npm start --prefix shell -- --demo`. The shell (Electron) starts the core from `.venv`. `uv run guildboard --demo --no-shell` runs the core alone and prints a link for the browser. `guildboard-app.exe --quit` (in a checkout: `shell\node_modules\electron\dist\electron.exe shell --quit`) asks the Guild Board that is running to quit, which may be your own installed copy: do not run it to stop a demo, stop the demo by its process.
- The shell has its own suites: `npm test --prefix shell` runs its unit tests and `npm run e2e --prefix shell` its browser tests of the window. Run them after the Python and interface suites, one at a time, never at once with them. The shell's e2e holds the check that the window writes only inside the data folder, and is run before a release. `shell/measure/` measures the window's frames, memory and start; never run it while the game runs: it captures the screen, and Guild Board never captures the game's.
- Make the installer to give Guild Board to someone else with `powershell -ExecutionPolicy Bypass -File build-installer.ps1`. It refuses to build until the release key is pinned in `selfupdate.py` (`-WithoutReleaseKey` builds an installer that never updates, and says so again at the end). It writes `dist-installer\Guild Board Setup <version>.exe` (about 130 MB), building the core in `.venv-package` so a running Guild Board keeps running and packing it into the Electron shell (`shell/build/package.mjs`); the recipes are in `packaging/`. The installer needs no administrator rights, and an update or an uninstall leaves the player's data.
- A public release has two halves. `.github/workflows/release.yml` runs on a tag `v<version>` (or by hand): it checks that the tag is the version in `pyproject.toml`, runs the Python, interface and shell tests, builds the installer with `build-installer.ps1` and attests it (`actions/attest-build-provenance`, skipped in a private repository). It holds no secret, no token and no release key, and it publishes nothing. Then `powershell -ExecutionPolicy Bypass -File tools\sign-release.ps1 -Tag v<version>` runs on the maintainer's PC: it needs `gh` logged in as `QL1STY` and `GUILDBOARD_RELEASE_KEY`, downloads the workflow's installer, checks its SHA-256 and `gh attestation verify`, makes a draft in `QL1STY/guild-board-releases`, signs the installer with the release key, and publishes only when the draft shows the signature beside it. `-NoAttestation` is for a trial on a private repository alone. A workflow's actions are pinned to a commit, and a workflow never reads `secrets.`; `tests/test_release_workflow.py` enforces both. `release.ps1`, which builds, signs and publishes on one PC, is the private checkout's way and is not in the public tree.
- The cache probe: `uv run python -m guildboard.pulls.cache_probe` reads the two files and prints what it found, never the key.
- The ledger probe: `uv run python -u -m guildboard.ledger.probe` reads the same two files and asks the game's history logs with the Feedback links' keys alone, the log's links first and then the cache's, the last written first in each, until one is accepted (open Feedback from the Paimon menu in the game first), printing counts and reasons, never a key; it only counts the wish links and names the other keyed links by address, so a wish key never goes to the history logs. `--login` asks with a key HoYoverse gives the HoYoLAB login instead, minted as Guild Board's own refresh mints it (the login's cookies go only to that mint request, never to the history logs), and reads no game file.
- The screenshot gallery (`gallery.py`) is off by default and turned on in Settings. It reads each picture through `gamecache.open_shared`, never opened from its path by anything else, and keeps its thumbnails in the data folder's `gallery-thumbs`. The demo's pictures are made in its own data folder, `demo-screenshots`, the first time its gallery looks; the demo never reads the game's.
- The online project's database lives in `cloud/migrations/`, applied in order to the project, and its SQL tests in `cloud/tests/`. Those run on the project itself, each in a transaction that never commits, and pass only when they end in the error `ALL PASSED` (`cloud/tests/README.md`). `cloud/README.md` says how a fork sets up its own project.
- Sync copies the player's own data to their account, table by table (`KINDS` in `src/guildboard/cloud/sync.py`, and schema 12's triggers in `store.py`). A new table the player makes rows in needs a decision: a kind of its own, with a migration that gives it its triggers, or a reason why it stays on the PC.
- Write the test first. Commit after each task.
- Messages the player can see are plain, factual English.
- Game art and the game's own text are not kept in this repository. The app reads HoYoverse's official pictures and wiki entries at runtime, into the player's local cache, and the demo does the same when it runs.

## The interface

- It lives in `web/` (React, TypeScript, Vite). Run its commands from that folder; run `npm install` once.
- `npm test` runs the unit tests. `npm run e2e` builds the interface and runs the browser tests, each against a fresh demo core, in the installed Microsoft Edge.
- The `npm run screens*` commands take pictures to be looked at, not tests that compare them. They write into the `screenshots` folder at the root of the repository, which git ignores (`GB_SCREENS_DIR` names another), each group in a folder of its own, and need nothing there first. `npm run screens` takes the stage 2A pictures (Achievements, Timers, Commissions, the Board, Stats, Backlog); the others take one group each: `screens:1b`, `screens:look` (the look pass, once its motion has settled), `screens:overlay` (closed, open and in Edit over a light and a dark stand-in for the game), `screens:scaling` (the usual window, 1,640 × 1,100, and full screen on 2,560 × 1,400), `screens:pulls`, `screens:topbar` (the top bar's plate in each sync state the demo can show, and the undo note), `screens:ledger` (Stats, the Ledger, Settings and the Gallery), `screens:characters`, `screens:friends`, `screens:stats` (the Overview with its Endgame card, a full month and a thin one, the Year and its two saved pictures), `screens:readme` and `screens:site` (the site's tabs, 1,640 × 1,000). Everything on them comes from the demo's made-up account and data.
- The public site is `site/` (a static page, no framework and no build step of its own: `index.html`, `site.css`, `site.js`) and is deployed by `.github/workflows/site.yml`. `tools/record-site-demo.py` records every answer the interface reads from the demo core (`tools/site_demo_core.py`, which names the demo's pictures by their official addresses) into `web/site-demo/recording`; `npm run build:site-demo` in `web/` builds the interface for `/guild-board/demo/` with `VITE_SITE_DEMO=1`, so that it reads the recording, refuses what a page sends and reads the pictures from HoYoverse's addresses (`web/src/sitedemo.ts`); `npm run screens:site` takes the site's screenshots into `screenshots/site`; `tools/assemble-site.py` puts the page, its self-hosted fonts, `demo/` and `shots/` together. To preview the page alone: `python -m http.server --directory site 8080`. The screenshots are never committed: they live on the branch `site-assets`, in `shots/`. `tests/test_site.py`, `tests/test_record_site_demo.py`, `tests/test_site_demo_build.py` and `tests/test_site_workflow.py` check all of it, and the installed app's bundle has none of the demo.
- `npm run build` writes `web/dist`, which the core serves. To look at it, run `uv run guildboard --demo --no-shell` and open the link it prints.
- The interface loads nothing from the internet and talks only to the core's local API. The one exception is the site's browser demo build (`VITE_SITE_DEMO=1`, never the installed app's), which has no core and reads the demo's pictures from HoYoverse's addresses. Times on screen follow the core's clock, never the browser's.
